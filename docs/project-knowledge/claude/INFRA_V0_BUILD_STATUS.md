# V0 infrastructure build status

Built on top of the core loop (`claude/UI_CORE_LOOP_BUILD_STATUS.md`) and the LOG ALLOY SESSION / HISTORY / EQUIPMENT / PROFILE screens (`claude/HISTORY_ALLOY_EQUIPMENT_PROFILE_BUILD_STATUS.md`). Scope was explicit and bounded: mobile installability/PWA, app icon/metadata placeholders, offline-safe behavior, data export, data import/restore, schema/version metadata, and basic error recovery — nothing else. Accounts, social features, nutrition, payments, cloud sync, AI chat, and gamification were explicitly excluded and none were added; every persistence/transfer mechanism built here stays on-device or moves through a file the person explicitly exports/imports themselves (never uploaded anywhere by the app).

## Meta + Settings persistence (D-108, P-09)

Two new real, persisted document types, seeded once on first run (`AppStore.loadOrSeedMeta` / `loadOrSeedSettings`):

- **`meta`** (`id: "meta"`): `app_schema_version` (D-108) and `installed_at`. Loaded *before* the datapack in `init()` specifically so a downgrade can be refused before any other work happens — a stored `app_schema_version` greater than this build's `APP_SCHEMA_VERSION` throws, which surfaces as `AppSnapshot.status: 'error'` with a clear message, rather than risking a silent misread of a future shape.
- **`settings`** (`id: "settings"`): device label (for telling backups apart — P-09, never read by the engine or any generation decision), units/tz defaults, sound/technical-detail toggles, and `last_export_at` (read by the Today-screen backup reminder below).

`AppSnapshot` now carries both. **No migrations exist yet** — `APP_SCHEMA_VERSION` has only ever been `1`, so only the seed path and the downgrade-refusal path have real code exercising them; §10.7's actual migration mechanism (pure `m<n>_to_<n+1>` functions, validate fully before writing) is not built. This is an honest gap, not a silently-skipped requirement: it has nothing to migrate yet.

## Data export / import — backup (D-107)

- **`src/app/backup.ts`**: a new `AppBackupSchema` (`format: "pto-backup-v0"`), **not** the canonical `contracts/backup.ts` `BackupSchema`. That schema assumes two things this app doesn't have yet: a full-replay engine (`replay()`, still unbuilt — same gap the B5 and core-loop status docs already flag) and the full canonical `Generation` record (this app persists a deliberately simplified `StoredGeneration`, per the core-loop status doc). Rather than silently forcing real data into a canonical shape it doesn't actually match — which would misrepresent what's stored, against this project's evidence-discipline rule — `AppBackupSchema` captures every actually-persisted document verbatim (`{id, type, ...}` passthrough), tagged with `app_schema_version`, `app_version`, a per-type document count, and a `state_digest` (`canonicalHash64` over the full document array, `src/domain/hash.ts`, already existed).
- **Export** (`AppStore.exportBackup`): builds the backup, names it `pto-backup_<YYYY-MM-DD>_<HHmm>.json`, and calls `platform/fileIO.ts`'s `saveJsonFile` — Web Share API Level 2 (file sharing) first, so it can go straight to iCloud Drive/Files/AirDrop on iOS, falling back to a plain Blob download on desktop. A share the person actually cancels (`AbortError`) is reported as `'cancelled'`, not silently followed by an unwanted download. Only bumps `settings.last_export_at` on a completed export.
- **Import** (`AppStore.pickAndPreviewBackup` / `previewBackup` / `restoreFromBackup`): opens the OS file picker (`platform/fileIO.ts`'s `pickJsonFile`), parses and validates before anything is written (format check, D-108's refuse-if-newer-version check), and only writes after the caller (Profile screen) has shown a confirmation sheet with real per-type counts. Restore fully replaces every document (`adapter.replaceAll`) and then re-runs `init()` — the same code path a normal launch uses, not a second, divergent "apply a restore" path.
- **Not encrypted in V0** (matches §10.9) — anyone with the exported file can read all of it.

## Crash / error recovery

Two distinct layers, both offering "export raw data" (`AppStore.exportRawData` — dumps whatever the adapter can still read, completely unvalidated, bypassing every schema check, since the point is to get data *out* when something is too corrupt for the normal export path) before a reload:

1. **`AppStore.init()` failure** (corrupt data, or a genuine downgrade refusal) — `AppSnapshot.status: 'error'`, surfaced by `App.tsx`'s existing error branch, now with "Export raw data" + "Reload" actions instead of a dead end.
2. **Any unhandled render/runtime crash** — a new `src/ui/ErrorBoundary.tsx` (class component, `getDerivedStateFromError`/`componentDidCatch`) wraps `<App />` in `main.tsx`. It reaches the same store instance via a new `getAppStore()` accessor exported alongside `useAppStore()` from `store.ts`, since a top-level boundary sits outside the tree that would normally call the hook.

## Storage persistence (§10.8)

`platform/storagePersistence.ts` wraps `navigator.storage.persist()`/`.persisted()` (Safari 17+; a no-op-safe `{supported: false}` elsewhere). Requested once, best-effort, on app mount (`App.tsx`); status shown in Profile with a manual retry button. This reduces — it does not eliminate — the odds of iOS evicting IndexedDB under storage pressure or 7-day inactivity; the backup export above is the actual safety net.

## Mobile installability / PWA

- **`public/manifest.webmanifest`**: name/short_name/description, `display: "standalone"`, three icon entries (192/512/512-maskable). `orientation` is deliberately **left unset** — the approved spec calls for "portrait-first with landscape allowed," and an explicit `portrait-primary` lock would contradict "landscape allowed"; the CSS itself stays portrait-first by design instead.
- **`index.html`**: manifest link, theme-color, description, favicon, and the `apple-mobile-web-app-*` meta tags + `apple-touch-icon` link iOS needs independently (iOS ignores the manifest's own icons/display mode).
- **Icons are placeholders**, per the instruction's own wording ("app icons / metadata placeholders") — a simple blue "P" monogram, not a designed mark. Generated by `tools/generate-icons.mjs`, a one-off script using the Playwright Chromium already installed for E2E tests to screenshot a tiny inline HTML element at each required size (192, 512, 512-maskable with extra safe-zone padding, 180 apple-touch, 32 favicon) — no new image-processing dependency added to the app itself. Re-run manually (`node tools/generate-icons.mjs`) whenever the placeholder should be regenerated or replaced with a real mark.

## Offline behavior + hand-written service worker (D-109)

- **`vite.config.ts`**: `build.manifest: true` — emits `dist/.vite/manifest.json`, mapping every entry/chunk/CSS/asset to its hashed build filename. This is what lets `public/sw.js` know exactly which files the *current* build needs precached without any bundler plugin (D-109 explicitly rejected Workbox/vite-plugin-pwa).
- **`public/sw.js`** (hand-written, plain unbundled JS — not part of the `src/` module graph, so the boundary rules don't apply to it): install fetches `/.vite/manifest.json` and precaches every referenced file plus `index.html` and the static `public/`-only PWA assets (manifest, icons — not in Vite's manifest since `public/` is copied verbatim); activate deletes every other `pto-*` cache; fetch is cache-first for same-origin GET, with navigations falling back to cached `index.html`. The cache name is a pure function of the resolved asset list (a tiny inline hash), so install and activate — which can run in different worker wake-ups, since an idle waiting worker can be killed and lose ordinary JS state — independently agree on it without storing anything extra.
- **`src/platform/serviceWorker.ts`**: registration + update primitives only (`platform -> domain`, no app/contracts knowledge). `AppStore` wires `onUpdateWaiting` in its constructor and calls `applyWaitingUpdate()` only from a new private `tryApplyPendingUpdate()`, gated on `activeWorkout?.status !== 'IN_PROGRESS'` — retried at the end of `init()` (on launch, and after a backup restore) and at the end of `finishWorkout()` (right after a session ends). `Profile.tsx` surfaces `AppSnapshot.updateAvailable` as a one-line status message; there's no manual "apply now" button since the two retry points already cover D-109's "on launch … otherwise it waits."

**Two real bugs found and fixed while verifying this end-to-end** (worth recording — both would have silently broken offline support in production):

1. **False update-reload on first-ever install.** `clients.claim()` in `sw.js`'s `activate` handler fires a `controllerchange` event on the page even the very first time a service worker ever takes control — not only when a real update replaces an existing one. The naive "reload on controllerchange" pattern (the common textbook example) was reloading the page immediately after its very first load. Fixed by gating the reload behind a module-level `expectingReload` flag in `serviceWorker.ts` that's only set inside `applyWaitingUpdate()` — i.e., the reload now only happens for a controller change this module itself asked for.
2. **`Vary: Origin` broke precache lookups for crossorigin assets.** Vite's own preview server (and plausibly other static hosts) sends `Vary: Origin` on every response. A `<script crossorigin>`/`<link crossorigin>` request sends an explicit `Origin` header even for a same-origin URL; the plain same-origin `fetch()` used inside the service worker's own `install` handler to populate the cache does not. Vary-aware cache matching then treated every precached JS/CSS file as a miss while offline (confirmed via a temporary debug script capturing the service worker's own console — icons and `index.html` matched fine, since those requests don't carry the extra `Origin` header; the JS bundle and stylesheet did not). Fixed with `{ ignoreVary: true }` on every `caches.match()` call in `sw.js`'s fetch handler — safe here since this service worker only ever caches its own build's own assets, never anything content- or origin-negotiated.

## Known gaps / recommended next steps

1. **No migration mechanism is actually exercised** — only the seed and downgrade-refusal paths have real code behind them, since `APP_SCHEMA_VERSION` has only ever been `1`. The first real schema change will need to build and test §10.7's `m<n>_to_<n+1>` pure-migration mechanism for real, not just refuse-if-newer.
2. **`AppBackupSchema` is a documented deviation** from the canonical `contracts/backup.ts` `BackupSchema` (see above) — restoring a backup replays nothing, it's a verbatim document swap. Correct for what this app actually persists today, but not what the canonical schema's field names would suggest if read in isolation from this doc.
3. **Icons are placeholders**, not a designed mark, per the instruction's own scope ("metadata placeholders").
4. **Backups are unencrypted JSON** (matches §10.9's "not encrypted in V0") — treat an exported file like any other unencrypted personal data file.
5. **The update-apply gate is checked at two points** (launch, right after a workout finishes), not continuously while idle — a long idle stretch on Today/History/Equipment/Profile with an update already waiting won't auto-apply until one of those two points recurs. Matches D-109's "on launch" wording; worth revisiting if idle sessions turn out to be long in practice.
6. **No real-Safari/WebKit verification** — same environment constraint as the two earlier status docs (this sandbox only has Chromium installed for Playwright). Service worker and Web Share behavior have known Safari-specific quirks (e.g. Web Share Level 2's file-sharing support, `navigator.storage.persist()` effectiveness) not exercised by this pass's Chromium-only E2E coverage — worth a manual spot-check on an actual iPhone before relying on offline/PWA behavior daily.
7. **The non-retraction limitation on Alloy log edit/delete** (documented in the previous status doc) is unaffected by this pass either way — a backup restore replaces documents rather than replaying history, so it neither fixes nor interacts with that gap.
